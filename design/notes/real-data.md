## 2. Sizes and dates (curl -sIL on 3 github release assets)
Chain: github.com/.../releases/download/<tag>/<file> -> 302 (content-length: 0, location: https://release-assets.githubusercontent.com/github-production-release-asset/<id>/<guid>?...sig=...jwt...) -> 200.
Exactly 1 redirect (num_redirects=1) in all 3 (KR-33 .nobp 45,593,718 B, last-modified Sun, 04 Oct 2026 13:22:31 GMT; ChimeraTailWeld zip 15,268 B, Thu, 28 May 2026 20:02:52 GMT; Multi-Missile.dll 73,520,128 B, Tue, 20 Oct 2026 07:15:54 GMT).
- The 302 itself has content-length 0 and NO last-modified. A HEAD without following is NOT enough. HEAD on the final (Azure blob) URL returns 200 with content-length, last-modified, etag, content-type application/octet-stream, no body (works; no GET needed).
- The signed Location expires after ~1 h (se= param); do not cache it. HEAD on the github.com URL each time.
- Date semantic: last-modified is the blob upload time (about the time the asset was uploaded), not the release publish date (atom `updated` was 13:24:48 vs last-modified 13:22:31 for KR-33).
- No x-ratelimit headers on github.com download URLs or on the Azure host. I did not hit any 429/403. Unverified: behaviour for 1324 HEADs in a burst; use limited parallelism (e.g. 4-8) and lazy fetch per visible/selected version, with a cache. api.github.com unauthenticated: 60 requests/h/IP (rate_limit endpoint showed limit 60); avoid the API, use the download URLs + atom.
- codeberg.org / discord CDN hosts not tested. Discord CDN links are signed/expiring and may fail.

## 3. Release notes (releases.atom)
GET https://github.com/<githubOwner>/<githubRepoName>/releases.atom -> 200 application/atom+xml, `cache-control: max-age=0, private, must-revalidate`, no rate-limit headers. Unknown repo -> 404. Repo renames redirect (dikkadev/... served the scramd/... feed through -L); use curl -L / follow redirects.
Feed: <feed> with <title>Release notes from <repo>, <updated>, up to 10 <entry> (KR-33: 2 entries; Multi-Missile: 10 entries while manifest lists 16 versions, so older versions have NO notes; confirmed: only 10 entries).
Entry fields: <id>tag:github.com,2008:Repository/<repoId>/<tag>, <updated> (ISO-8601 UTC, "2026-10-04T13:24:48Z"; this is the publish/update time), <link rel="alternate" type="text/html" href=".../releases/tag/<tag>"/>, <title> (the RELEASE NAME; may differ from the tag, e.g. "1.5.0 - <name>", "NuclearMapPan 0.1.1", "Nuclear Option Modpack -mine 1.2.1"), <content type="html"> (all 10+2+10 entries: type="html"; the body is XML-escaped HTML, e.g. &lt;h3&gt;...; unescape once, then render/sanitise HTML; the body can be empty), <author><name>login</name>, <media:thumbnail url=avatar>.
Mapping entry -> version: take the TAG, not the title. Tag = last path segment of the entry link href after /releases/tag/ (percent-decoded), also the 3rd-from-end segment of an artifact downloadUrl: `.../releases/download/<tag>/<file>`. Match artifact.downloadUrl tag == entry tag (exact; this is robust: KR-33 "V1.0.1" tag vs version "1.0.1" does not match by string, only via the URL). Fallback: strip releaseTagPrefix (if set) and a leading v/V, compare as versions. Monorepos (dikkadev/scramd nuclear-option-client-mods) hold many mods in one feed, tags like NuclearMapPan-v0.1.1, Modpack-mine-v1.2.1: group by tag prefix, and fetch each feed once per repo (cache by repo).
Old NOMM did not fetch release notes (git grep for atom/githubOwner/release notes found nothing; the manifest's githubOwner/githubRepoName are not even in the old Extension class, Manifest.kt:12-26).

## 6. Game version without starting the game
Nothing in the old code reads it from disk (see 4). Candidates (NOT verified, no game files here):
- Steam: <library>/steamapps/appmanifest_2168680.acf (VDF): has "buildid" (integer Steam build number, NOT the 0.34.x string), "installdir", "name", "LastUpdated", "TargetBuildID". Good to detect "game updated since last check", can't compare with manifest gameVersion directly (needs a table buildid -> version, which does not exist).
- Unity: NuclearOption_Data/globalgamemanagers (binary asset file; PlayerSettings.bundleVersion string = the Application.version the developer set, plausibly "0.34.x"), NuclearOption_Data/app.info (2 text lines: company and product name, no version), NuclearOption_Data/boot.config (no version), UnityPlayer.dll file version = Unity engine version (not the game). Realistic way: scan globalgamemanagers bytes for the bundleVersion (string search near product name "NuclearOption" / pattern \d+\.\d+(\.\d+)?), validate on a real install first. Also: BepInEx/LogOutput.log after a modded start contains "Running under Unity v<engine>" (engine only) and the game version only if a mod logs it. NuclearOption.exe PE file version info: check with a real file (unverified).
- Fallback: Steam rules key "v" for servers is the game version (ServerDetailScreen.kt:473) -- shows what the game reports itself (so it is "0.34.x"-shaped) but needs a server query.
Conclusion: realistic = (1) parse buildid from appmanifest as change detector and (2) try globalgamemanagers/exe version resource, behind a "version unknown" fallback; ask the user to run a real install to confirm. Old NOMM used no detection and compared only mod gameVersion vs the highest manifest gameVersion.
